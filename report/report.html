Single-core throughput · JSON and one Postgres query

TanStack Start Cloudflare Workers versus FastAPI Python

Realistically, my choice for a new API is between a TanStack Start app with its routes built in and a standalone FastAPI server1. So I put both on a single pinned core against the same local Postgres, served byte-identical responses, and measured how much each serves and whether the choice even matters once a database enters the path. There are plenty of caveats, so this was more an experiment than anything else.

How it was run

Methodology & disclosure

  • Contenders. A TanStack Start server route (Zod + postgres.js over cloudflare:sockets)2, built for Cloudflare and served under raw workerd serve, versus uvicorn[standard] (uvloop + httptools, 1 worker, async def) + FastAPI + Pydantic + ORJSONResponse + asyncpg. Both fully tuned, configs in the repo. The framework is part of each stack, since you don't swap the API layer under Start. A raw fetch handler on the same workerd gives the zero-framework reference number.
  • Identical work. Byte-for-byte identical responses; /echo validates input on both sides (Zod / Pydantic) and serializes per request; /db returns one random-PK row, no caching.
  • Isolation. The server is pinned to one core (taskset, HT sibling avoided); Postgres and k6 run on separate cores; placement is verified with mpstat during the run6.
  • Transport. Host networking, HTTP/1.1, keep-alive, no TLS, with identical k6 config on both sides (open model, so connections scale with offered load).
  • Determinism. Governor performance, turbo disabled, box quiesced; connection pool 10 on both sides; payload identical.
  • Load. k6 open-model arrival-rate executors: discrete constant-arrival-rate steps to find the knee, then a sub-saturation constant rate for latency (no coordinated omission)3. maxVUs oversized; dropped_iterations asserted zero.
  • Protocol. Warmup is discarded after p99 flattens, then contenders run one at a time, alternating order (AB, BA) so first-mover effects cancel. Results are median ± IQR with error bars on every chart.
  • Footprint. RSS is read from the cgroup at idle after warmup; CPU-time per request comes from cgroup CPU accounting over a fixed-rate run, divided by requests served.

Takeaways

What did we learn?

We applied the classic research-oriented framework “what did we learn” to pull the useful insights out of this benchmark.

  • A stack comparison, not a language shootout. Everything differs between the corners: runtime (V8 vs CPython), HTTP server, framework (TanStack Start vs FastAPI) and DB driver. That is on purpose, because it reflects the real choice: the whole stack you would ship rather than a bare runtime. The raw-fetch number isolates how much of the /echo gap is runtime versus framework.
  • workerd isn't tuned for standalone throughput. Cloudflare's own repo notes the open-source runtime hasn't had performance tuning, and they've seen ~2× on a hello-world load test from compiler flags and allocator changes alone5. So workerd's numbers here are a conservative lower bound for the Workers runtime, not its ceiling.
  • Per-core efficiency, not scalability. Real Cloudflare auto-scales to thousands of isolates; we cage workerd to one core. This is not "max RPS from Workers", so multiply by cores for a rough fleet estimate.
  • Local workerd ≠ production Workers. No cold starts, eviction, multi-tenant scheduling, or placement/network. A clean upper bound on the runtime, not deployed behaviour.
  • Direct DB is not the production topology. At scale you'd front Postgres with Hyperdrive or pgbouncer, which would help the Worker rather than hurt it.
  • Two narrow tests. JSON serialization and a single-row read only, with no write paths, templating/XSS, multi-query scaling, or routing ceilings.
  • The DB tie is the headline, not a footnote. Most real apps are DB-bound, so for typical CRUD the runtime choice barely moves throughput. That is the honest finding.
Reproduce

Run it yourself

git clone <repo> && cd tanstack-start-vs-fastapi
./run.sh            # pins cores, disables turbo, warms up, sweeps the knee, alternating bouts
python analyze.py   # raw k6 JSON, median/IQR, results.js, this page

The repo ships pinned lockfiles, Dockerfiles with image digests, the run script, raw per-run k6 JSON (so anyone can recompute percentiles and check for coordinated omission), and the chart-generation script.

References

Notes & sources

  1. Standalone FastAPI, not Cloudflare Python Workers. Cloudflare can run Python on Workers via Pyodide (CPython compiled to WASM), but it's a young runtime: slower than native CPython, heavy cold starts, a limited package set, and no native asyncpg, so a real FastAPI + Postgres app can't run there as-is. FastAPI is measured where it actually ships, on native CPython + uvicorn; both contenders still share the same pinned core. Cloudflare Python Workers docs
  2. postgres.js over cloudflare:sockets. The Worker reaches Postgres over Cloudflare's raw TCP socket API, which postgres.js supports directly, so the query path is a real driver round-trip rather than a proxy. porsager/postgres
  3. Open-model load avoids coordinated omission. k6 arrival-rate executors fire requests on a fixed schedule regardless of response time, so a slow server can't mask its own latency by simply sending fewer requests. wrk2 and Gil Tene on coordinated omission
  4. Cloudflare bills CPU time, not wall-clock. Workers charges for CPU time per request while I/O wait is free, which is why CPU-ms per request is both the efficiency metric and the actual bill. Cloudflare Workers pricing
  5. workerd is a conservative lower bound. Cloudflare notes the open-source runtime hasn't had standalone performance tuning and has seen roughly 2× from compiler flags and allocator changes alone, so these numbers understate the Workers runtime rather than flatter it. cloudflare/workerd · CPU performance benchmarks
  6. Benchmarking discipline. Single-core pinning, warmup, governor and turbo control, and percentile-based latency follow standard systems-benchmarking practice. Brendan Gregg's benchmarking checklist
